Antes de arrancar

AI Engineering es construir el sistema, no perfeccionar el prompt

No es escribirle bonito a un modelo. Es la disciplina de construir un sistema de software confiable alrededor de un modelo — contratos, validación, políticas y observabilidad — para que una herramienta creativa pero probabilística se comporte de forma predecible dentro de un producto real.

  • El modelo interpreta lenguaje natural y propone.
  • La capa de aplicación — el código que ustedes escriben — decide qué se ejecuta.
  • Esa separación es todo lo que vimos ayer, y es la base de todo lo de hoy.

Ayer armaron un contrato, no solo un prompt

01

Contexto explícito

Instrucciones, política de negocio y restricciones dadas al modelo antes de la llamada — incluyendo tratar el input como dato no confiable.

Por qué importa: sin esto el modelo responde con conocimiento general, no con las reglas reales del negocio.
02

Salida estructurada

Un contrato Pydantic (AnalisisIncidente) que convierte texto libre en un objeto tipado y validado.

Por qué importa: una respuesta "convincente" en texto no es un contrato de software.
03

Encapsulamiento

La llamada al modelo vive dentro de una función (analizar_incidente()), aislada del resto de la app.

Por qué importa: permite cambiar de proveedor sin tocar nada más — hoy lo van a comprobar.

Profundizando · Salida estructurada

Pydantic no es la única opción★

Pydantic es una librería de Python: define la forma de un dato como una clase (BaseModel) y la valida automáticamente en tiempo de ejecución — si algo no cumple el tipo o la regla, se corta ahí con un error, no sigue de largo. Además genera un JSON Schema a partir de esa clase, que es exactamente lo que consumen las APIs de OpenAI y DeepSeek para forzar la salida estructurada.

  • dataclasses (de la librería estándar) — liviano, pero sin validación automática: hay que escribirla a mano.
  • attrs + cattrs — separa la definición de la clase (attrs) de la serialización/validación (cattrs).
  • marshmallow — pensado para serializar/deserializar APIs REST; el schema se define aparte de la clase.
  • TypedDict — solo tipado para el editor/mypy, cero validación real en ejecución.
  • jsonschema — validar a mano contra un JSON Schema escrito directo, sin clases de Python.
  • Zod — si trabajan en JavaScript/TypeScript, es el equivalente casi 1:1 de Pydantic.

Por qué Pydantic ganó terreno en LLMs: genera el JSON Schema automáticamente, y es el estándar de facto en frameworks como LangChain, LlamaIndex, Instructor y PydanticAI. No es la única forma de validar datos — es la que mejor conecta con las APIs de modelos de hoy.

Las reglas que hacen que confíen en la salida

04

Observabilidad

Tokens de entrada/salida y latencia registrados en cada llamada, junto con la versión de modelo usada.

Por qué importa: sin esto es imposible depurar ni comparar modelos cuando algo falla.
05

Políticas deterministas

Reglas de código (if/else) sobre el resultado, no el modelo decidiendo solo.

Por qué importa: la autorización real nunca depende únicamente de una salida probabilística.
06

Abstención / HITL

Un valor válido de "no tengo evidencia suficiente" (no_determinada) en vez de forzar siempre una respuesta.

Por qué importa: evita que el modelo finja certeza — peligroso en sistemas críticos.

Quedó pendiente: el dataset de casos de prueba que armaron ayer para evals deterministas no llegó a correrse por tiempo, y no llegaron al puente entre clasificación y acción. Hoy arrancamos justo ahí.

Profundizando · Políticas deterministas

if/else no es la única forma de decidir★

La política que vimos (if categoria == "SEGURIDAD"...) es perfecta para 2 o 3 reglas simples y explícitas. El problema aparece cuando el negocio agrega la regla número 15: un árbol de if/else anidados se vuelve difícil de leer, de testear y de auditar.

if / else

Reglas de código, explícitas, leíbles de arriba a abajo. Cada regla nueva es una rama más en el mismo árbol.

Usalo cuando: tenés pocas reglas (2-5), estables, y todo el equipo las puede leer en una pantalla.

Router

Un componente único —una tabla de reglas, un clasificador, a veces otro LLM chico— decide a qué handler mandar cada caso. Cada handler se prueba por separado.

Usalo cuando: las reglas son muchas, cambian seguido, o vienen directo del negocio (ej. LangGraph, Semantic Router).

No es una migración obligatoria: es una señal a vigilar. El día que el if/else deja de entrar en una pantalla, es momento de pensar en un router.

Nota técnica

Hoy cambiamos de proveedor: DeepSeek★

Ayer usamos OpenAI. Hoy usamos DeepSeek a propósito — para demostrar en vivo por qué sirvió haber encapsulado la llamada al modelo.

# Mismo SDK de OpenAI, solo cambia el destino
from openai import OpenAI

client = OpenAI(
  api_key=DEEPSEEK_API_KEY,
  base_url="https://api.deepseek.com"
)

Lo que sí cambia: DeepSeek no fuerza el JSON Schema tan estrictamente como el strict=True de OpenAI — usa response_format={"type": "json_object"}. Por eso hoy agregamos una validación explícita con Pydantic después de la llamada, con reintento si falla. No es un parche: es la misma lección de ayer, un nivel más abajo — nunca confiar ciegamente en lo que devuelve el modelo.
